# Task Priority Management Requirements

**Project:** Mini Todo Application  
**Document status:** Approved after human review  
**Source of truth:** Existing repository code and the approved product decisions recorded below

## 1. Project overview and existing functionality

The application is a Java Spring Boot Todo application using Spring MVC, Thymeleaf, Spring Data JPA, and an in-memory H2 database. The current `Task` entity contains:

- `id`, generated by the database
- `description`
- `date`, stored as a date and formatted as `yyyy-MM-dd`

The web controller is mapped under `/todo`:

- `GET /todo/home` lists tasks and renders `home.html`.
- `POST /todo/addTask` creates a task after checking that its description is not numeric-only and is at least five characters long.
- `GET /todo/updateTask/{id}` loads a task into `updateForm.html`.
- `POST /todo/saveUpdate` updates a task's description and date.
- `GET /todo/deleteTask/{id}` deletes a task.
- `GET /todo/backHome` redirects to the home page.

The REST controller is mapped under `/api/todo`:

- `GET /api/todo/task/{id}`
- `GET /api/todo/tasksList`
- `POST /api/todo/add`
- `PUT /api/todo/update/{id}`
- `DELETE /api/todo/delete/{id}`

The Thymeleaf templates are `home.html` and `updateForm.html`. They currently provide task creation, listing, editing, and deletion controls for description and target date. The persistence flow is entity -> repository -> DAO -> service -> controller. The only existing automated test is a Spring context-load test; there are no existing behavior or controller tests.

## 2. Problem statement and identified gaps

Users currently cannot indicate the relative importance of a task. The entity, persistence flow, web forms, task list, REST request/response model, and update methods have no priority field or validation.

The enhancement must add exactly three supported priorities—High, Medium, and Low—while preserving the existing task fields and CRUD behavior. New tasks must have a priority, existing tasks must receive `MEDIUM`, and priority must work through both the web UI and REST API. Displaying priority is in scope; sorting and filtering are not.

## 3. Scope

### In scope

- Add task priority with the values `HIGH`, `MEDIUM`, and `LOW`.
- Require priority when creating tasks through the web UI and REST API.
- Display priority in the task list.
- Show and allow changing priority in the update form.
- Accept and return priority through the REST API.
- Validate priority server-side.
- Assign `MEDIUM` to existing tasks during migration or upgrade.
- Preserve description, date, ID, and existing create/update/delete/list behavior.
- Add automated coverage for the new priority behavior as part of implementation.

### Out of scope

- Priority sorting.
- Priority filtering or search.
- Additional priority levels or custom priorities.
- Task status, reminders, notifications, authentication, authorization, or user-specific task lists.
- Changes to the existing description rules, date behavior, URL structure, or database technology unless required to implement the approved priority field.
- Redesign of the application's visual style.

## 4. Functional requirements

| ID | Requirement |
|---|---|
| FR-001 | The system shall represent task priority using exactly `HIGH`, `MEDIUM`, or `LOW`. |
| FR-002 | The system shall require a valid priority for every newly created task. There shall be no default for a new task when the value is missing. |
| FR-003 | The system shall persist priority with the task without changing the existing `id`, `description`, or `date` semantics. |
| FR-004 | The web create form shall provide a required priority control containing High, Medium, and Low. |
| FR-005 | The web task list shall display a Priority column for every task. |
| FR-006 | The web update form shall show the task's current priority as selected. |
| FR-007 | The web update form shall allow the user to replace the current priority with any of the three valid values. |
| FR-008 | A valid web create or update shall persist the selected priority and return the user to the existing task-list flow. |
| FR-009 | The system shall preserve the existing description validation and task CRUD operations. |
| FR-010 | `POST /api/todo/add` shall accept and persist a valid priority. |
| FR-011 | `PUT /api/todo/update/{id}` shall accept and persist a valid priority while retaining the existing update behavior for description and date. |
| FR-012 | `GET /api/todo/task/{id}` and `GET /api/todo/tasksList` shall include priority in returned task JSON. |
| FR-013 | Invalid or missing priority values shall not be persisted. |
| FR-014 | Existing tasks shall receive `MEDIUM` during the priority migration or upgrade. |
| FR-015 | The application shall preserve the existing task-list ordering; adding priority shall not sort or filter tasks. |

## 5. Non-functional requirements

| ID | Requirement |
|---|---|
| NFR-001 | Priority validation shall be enforced server-side for both form submissions and REST requests; browser controls alone shall not be trusted. |
| NFR-002 | Priority values shall be type-safe and constrained to the supported set rather than being accepted as arbitrary free text. |
| NFR-003 | Invalid REST priority input shall produce an appropriate 4xx client error with a meaningful validation response, not a successful response or silent fallback. |
| NFR-004 | Invalid web priority input shall redisplay the relevant form with an understandable error and preserve the user's valid entered values where possible. |
| NFR-005 | Existing tasks shall retain their IDs, descriptions, dates, and other existing data during migration. |
| NFR-006 | The priority implementation shall not require an additional database query per task when rendering the existing list. |
| NFR-007 | Existing API fields and CRUD endpoints shall remain available; priority shall be additive to the task representation. |
| NFR-008 | Automated tests shall cover valid values, invalid and missing values, persistence, web flows, REST flows, and migration behavior. |
| NFR-009 | Priority labels and controls shall be understandable and consistently named across the web UI and API. |

## 6. Approved product decisions

The following four decisions were approved by the product stakeholder:

1. **New-task priority:** Priority is mandatory for new tasks; there is no default when it is omitted.
2. **Channels:** Priority management applies to both the Thymeleaf web UI and the REST API.
3. **List behavior:** The task list displays priority only. Sorting and filtering by priority are out of scope; existing ordering is preserved.
4. **Existing data:** Existing tasks receive `MEDIUM` when the feature is introduced.

## 7. Acceptance criteria

### AC-001: Create a task with priority

**Given** the user is on the task creation form  
**When** the user enters a valid description and date, selects High, Medium, or Low, and submits  
**Then** the task is saved with the selected priority and the priority is shown in the task list.

### AC-002: Require priority in the web UI

**Given** the user is creating a task  
**When** the user submits without a priority  
**Then** the task is not saved, an understandable validation message is shown, and the form retains the other valid inputs where possible.

### AC-003: Display priority

**Given** tasks exist with valid priorities  
**When** the user opens `/todo/home`  
**Then** each task displays its priority in a dedicated column and the existing task order is unchanged.

### AC-004: Edit priority

**Given** an existing task has a priority  
**When** the user opens its update form  
**Then** the current priority is selected; and when the user selects another valid priority and saves, the stored priority changes without losing the task's ID, description, or date.

### AC-005: REST create

**Given** a client sends `POST /api/todo/add` with valid task fields and a valid priority  
**When** the request is processed  
**Then** the task is created and the returned task representation includes the selected priority.

### AC-006: REST update

**Given** an existing task  
**When** a client sends `PUT /api/todo/update/{id}` with a valid priority  
**Then** the task's priority is updated and subsequent GET requests return the new value.

### AC-007: Reject invalid REST priority

**Given** a client sends a missing, blank, unsupported, or malformed priority  
**When** the client calls the create or update endpoint  
**Then** the request is rejected with a 4xx validation response and no invalid value is persisted.

### AC-008: Migrate existing tasks

**Given** tasks were created before priority management existed  
**When** the application is upgraded  
**Then** those tasks receive `MEDIUM` while retaining their existing IDs, descriptions, and dates.

## 8. Edge cases and validation rules

- Supported values are exactly `HIGH`, `MEDIUM`, and `LOW` at the domain/API level. The web UI may display them as High, Medium, and Low.
- Missing priority on a new web submission is a validation failure; it must not silently become Medium.
- Missing priority in a create or update REST request is a 4xx validation failure.
- Blank, whitespace-only, unsupported, or malformed priority values are invalid and must not be persisted.
- Case normalization may be applied only if it is explicitly implemented consistently; otherwise non-canonical REST values must be rejected. The canonical stored/API values are `HIGH`, `MEDIUM`, and `LOW`.
- If description validation and priority validation both fail, the response must remain a validation response and must not save the task.
- A web validation response should preserve the selected priority and other valid submitted values where possible.
- Existing null priority values encountered during migration must be converted to `MEDIUM`.
- A task update must not reset priority, description, or date fields that were not being changed.
- Requests for nonexistent task IDs must preserve the application's existing not-found/error behavior; priority handling must not create a new task implicitly.

## 9. REST API requirements

Priority is additive to the existing `Task` JSON representation.

| Method | Endpoint | Priority behavior |
|---|---|---|
| GET | `/api/todo/task/{id}` | Return the task, including its priority. |
| GET | `/api/todo/tasksList` | Return every task with its priority. |
| POST | `/api/todo/add` | Require and persist a valid priority; reject missing or invalid values with 4xx. |
| PUT | `/api/todo/update/{id}` | Require and persist a valid priority; retain existing description/date update behavior. |
| DELETE | `/api/todo/delete/{id}` | Continue existing deletion behavior; priority requires no special delete operation. |

REST clients must not be able to bypass server-side priority validation by sending arbitrary JSON. Existing fields (`id`, `description`, and `date`) remain part of the task representation and existing endpoints remain available.

## 10. Backward compatibility and existing-task migration

The enhancement shall preserve current web routes, REST routes, task IDs, descriptions, target dates, and CRUD behavior. Priority is an additional task attribute, not a replacement for any current field.

Existing records created before the enhancement shall be assigned `MEDIUM`. The implementation must use a migration or upgrade-safe initialization strategy that handles existing rows without data loss. After migration, every task returned by the web UI or REST API must have one of the three valid priority values.

Because the current database is configured as an in-memory H2 database, existing data is not durable across application restarts in the current configuration. The migration requirement nevertheless applies to any existing rows present when the upgraded application initializes and to any future persistent deployment.

## 11. Assumptions, dependencies, and risks

### Assumptions

- High, Medium, and Low are sufficient; no custom priorities are needed.
- Priority is descriptive only and does not alter task execution, reminders, or ordering.
- The current `/todo` and `/api/todo` route structures remain unchanged.
- A new task must explicitly provide priority, while legacy tasks are the only records eligible for automatic `MEDIUM` assignment.

### Dependencies

- The `Task` entity, DAO, service, controllers, and both Thymeleaf templates must be able to carry the new field.
- Spring MVC data binding and JSON conversion must support the chosen type-safe priority representation.
- The database schema or migration mechanism must support a priority column and legacy-row backfill.
- Automated tests must be expanded beyond the current context-load-only test.

### Risks

- A schema change without a backfill could leave existing tasks null or make application startup fail.
- Updating only the web UI or only the REST API could create inconsistent task data.
- Accepting arbitrary strings could introduce invalid values that break display or future reporting.
- Replacing the existing update method without retaining description/date behavior could cause data loss.
- The current H2 in-memory configuration can make manual migration verification non-durable.
